# RED/GREEN contract implementation plan

> Execute inline with the executing-plans and test-driven-development skills. User authorized implementation with “go.”

Goal: replay frozen tests against prior and candidate behavior, accepting only declared assertion failures as RED evidence. Keep local execution serial and preserve the original dirty clone.

Contract: a manifest in `.red-green/` declares a full baseline commit and uniquely named cases with expected baseline pass/fail outcomes. Each claim needs at least one distinguishing failure. The last manifest-editing commit is the tests commit. Every intervening commit from baseline through tests must change only tests/fixtures and manifests. Implementation must preserve the declared tests, supporting test files, and shared harness. Both phases use the tests commit's frozen test tree; the implementation controls production code/configuration. Assertion fingerprints compare operator, actual, expected and ERR_ASSERTION, not merely exit codes. Missing/extra/skipped/todo/cancelled tests, setup/import/parser errors, process crashes and timeouts invalidate evidence. Candidate must pass all frozen tests. Existing tests must remain green in baseline too.

Scope: source, rule implementations, compiler/lint configuration and dependency/script changes require an active contract. Documentation-only and test/harness preparation changes can remain green without a behavior claim; they are identified as preparation rather than RED/GREEN proof. Bootstrap is necessary because the verifier is absent from the current base. Bootstrap is not a retroactive claim that earlier PRs followed this contract.

1. Protocol and evidence (scripts/red-green/{model,evidence,reporter}.ts, tests/red-green/protocol.test.ts): write and observe failing semantic tests, implement strict manifest/report parsing and exact outcome checks. Use Node's structured events, not TAP string heuristics. Named case identity is file plus unique test name; controls can pass in both phases.
2. History and execution (scripts/red-green/{git,replay,verify}.ts, scripts/check-red-green.ts, tests/red-green/history.integration.test.ts): isolated Git fixture histories test valid pairs, test-only RED, source edits before tests, changed/removed tests and harness, arbitrary baseline refs, missing manifests, unexpected failures, false GREEN, dependencies and process cleanup. Replay in disposable exact Git snapshots with fixed serial runner, bounded heap/time/output and isolated environment. No worktree/checkouts in the user's clone. Include a real lint configuration pair to exercise the existing harness without an enabled-rule setup failure.
3. CI and usage (.github/workflows/red-green.yml, package scripts, docs/red-green.md): verifier is loaded from the default branch, tests from the declared tests commit, production from baseline/head. Use a read-only pull_request_target job, no secrets or caches and no persisted checkout credentials; untrusted test subprocesses receive only an isolated environment. Existing verify job still requires the full current suite to pass, keeping tests-only PRs red. Full fetch is required. Explain bootstrap, pair merging, stable-case assertions and limitations. Do not change branch protection until bootstrap is merged, because doing so now would block the existing reviewed stack.
4. Verify serially, independent fresh-context review, fix Important findings with regressions, open draft stack addition(s), attach PRs and inspect CI. Do not force-push or merge the user's stack.

Review focus: commit-order manipulation, manifest tampering, omitted tests, false expected failures, shared harness/dependency changes, Node event differences, false skips, environment/preload injection, process descendants, Git path/ref safety, archive exports, workflow trust and bootstrap limitations.

## Execution rulings and evidence

- User selected a fast local default with integrations required in CI. Use explicit static unit/integration entries, with a discovery inventory test to reject omissions; run locally serially and allow two CI entries in parallel.
- Repeated cold compiler/program setup dominated runtime. Reuse versioned TypeScript language services within each fixture project and a document registry across them; compare warm diagnostics with cold programs through import additions/removals/edits. Small in-project lint configs avoid incompatible parser singleton settings in a shared process.
- Budget warnings are observational: 100 ms/case, 10 seconds/run, including setup; malformed configuration warns and falls back. No timing failure or automatic timeout is inferred from these budgets.
- Only deliberately marked plain-JSON behavior assertions qualify as RED. Ordinary Node assertions and import/parser/setup failures remain rejected even if they look like assertion failures.
- Bootstrap is reviewed normally and does not claim historical self-verification. Subsequent changes use frozen tests-first pairs. Split execution foundations from checker/CI bootstrap so both are independently reviewable.
- Measured local fast suite: 513 passing, 8.48 seconds runner time; one process peaked at 1.25 GiB RSS (V8 heap capped at 1 GiB). Full integrations run separately and are not omitted in CI.
